## 2024-06-29 - Fixed CSRF Vulnerability in OAuth Consent Form

**Vulnerability:** A CSRF (Cross-Site Request Forgery) vulnerability allowed any website to trigger the OAuth authorization consent form via a direct POST request without the user's authorization or intent, potentially leaking the authorization code or granting access.
**Learning:** The absence of CSRF protection token validation, particularly using standard stateful or stateless paradigms like Double Submit Cookie, in endpoints that serve state-changing POST forms can lead to unintended approvals of authorization grants.
**Prevention:** Ensured the consent GET form correctly embeds a stateless cryptographic CSRF token, and required its presence and validation against a secure `Lax` or `Strict` cookie upon the subsequent POST request. Also, set the `X-Frame-Options: DENY` header on the consent form page to prevent Clickjacking.
## 2024-06-30 - Fix DoS via UnicodeDecodeError in Middleware
**Vulnerability:** A Denial of Service (DoS) vulnerability was found in `OAuthMiddleware`. Calling `headers.get(b"authorization", b"").decode()` blindly crashes the server (500 Error) if a user supplies invalid UTF-8 bytes in the `Authorization` header.
**Learning:** Starlette/ASGI apps deliver headers as raw bytes. Blindly decoding them to UTF-8 without a try/except block introduces unhandled exceptions that attackers can easily trigger to bypass logic or crash endpoints.
**Prevention:** Always read headers as raw bytes. Validate known prefixes (like `b"Bearer "`) using byte strings. Wrap any `.decode()` calls in a try-except block handling `UnicodeDecodeError`, failing gracefully (e.g., returning 401 instead of 500).
## 2024-07-01 - Fix ASGI Protocol Violation DoS in WebSocket Middleware
**Vulnerability:** A Denial of Service (DoS) vulnerability existed in `OAuthMiddleware`. When a client established an unauthenticated WebSocket connection (`scope["type"] == "websocket"`), the middleware attempted to reject it by calling `_send_json`, which dispatches HTTP response events (`http.response.start`). Sending HTTP events over an ASGI websocket scope causes the ASGI server (e.g., Uvicorn) to crash the connection with a `RuntimeError` due to a protocol violation, rather than failing securely.
**Learning:** Middleware handling both HTTP and WebSockets must respect ASGI protocol differences. Security rejections (like 401 Unauthorized) cannot be sent identically to both connection types. WebSockets require explicit `{"type": "websocket.close", "code": 1008}` events to indicate policy violations.
**Prevention:** Always check `scope["type"]` before sending rejection events in middleware. Ensure that WebSocket rejections dispatch `websocket.close` with an appropriate code (e.g., 1008 Policy Violation) instead of reusing HTTP-specific error handlers.
## 2024-07-02 - Add Cache-Control Headers to Prevent Credential Leakage
**Vulnerability:** The `/register` and `/token` endpoints previously returned JSON responses containing sensitive data (e.g., `client_secret` and `access_token`) without explicitly forbidding caching. This creates a risk where intermediary proxies or browser caches could store these secrets, leading to credential leakage.
**Learning:** Returning sensitive credentials in HTTP responses requires explicit headers (`Cache-Control: no-store` and `Pragma: no-cache`) to ensure they are not cached by any network intermediaries, as mandated by OAuth 2.0 (RFC 6749) and OAuth 2.0 Dynamic Client Registration (RFC 7591).
**Prevention:** Always ensure that endpoints returning access tokens, refresh tokens, client secrets, or other sensitive authentication materials include `headers={"Cache-Control": "no-store", "Pragma": "no-cache"}` in the HTTP response.
## 2024-07-06 - Prevent DoS via Invalid JSON Type in Register Endpoint
**Vulnerability:** A minor Denial of Service (DoS) vulnerability existed in the `/register` endpoint because `body = await request.json()` does not guarantee the parsed JSON is a dictionary. If a client sends a JSON array or string (e.g., `["foo"]`), the subsequent call to `body.get()` triggers an `AttributeError`, resulting in a 500 Internal Server Error crash.
**Learning:** `request.json()` can return lists, strings, ints, or booleans depending on the client payload. Applications must actively type-check the returned parsed JSON before interacting with it to ensure stability.
**Prevention:** Always use `isinstance(body, dict)` after parsing JSON to ensure it is the expected dictionary before performing `.get()` or dictionary lookups on the payload.
## 2025-02-14 - SSRF/CIMD Bypass in Authorization Endpoint
**Vulnerability:** The `/authorize` endpoint unconditionally fetched Client ID Metadata Documents (CIMD) for unknown HTTPS client IDs, even when `public_registration` was set to `False`. This bypassed the private registration mode and exposed the server to potential Server-Side Request Forgery (SSRF) and Denial of Service (DoS).
**Learning:** External or remote fetches based on user-supplied input must be strictly gated by application configuration state, not just input validation.
**Prevention:** Ensure feature flags (like `public_registration`) are validated *before* initiating any external network requests or dynamic registration workflows.
## 2025-02-20 - Fix DoS via ValueError in urlparse for Malicious URLs
**Vulnerability:** A Denial of Service (DoS) vulnerability existed in `origo/endpoints.py`. Unvalidated user-supplied inputs (`client_id` and `redirect_uris`) were passed directly to `urllib.parse.urlparse`. Malformed URLs (such as `https://]/`) cause `urlparse` to raise an uncaught `ValueError` (e.g., "Invalid IPv6 URL"). This unhandled exception caused the ASGI server to return a 500 Internal Server Error, allowing attackers to easily crash request handling on critical endpoints like `/authorize` and `/register`.
**Learning:** `urllib.parse.urlparse` is not completely safe to call on arbitrary string inputs in recent Python versions; it actively validates parts of the URL structure (like IPv6 brackets and port ranges) and can raise exceptions that must be handled by robust web applications.
**Prevention:** Always wrap `urlparse` calls dealing with untrusted user input in a `try...except ValueError` block to safely catch parsing errors and return appropriate validation failures (like 400 Bad Request) instead of crashing.

## 2025-02-21 - Fix DoS and Prevent CRLF in _build_redirect
**Vulnerability:** A Denial of Service (DoS) vulnerability existed in `origo/endpoints.py` where `_build_redirect` called `urllib.parse.urlparse` on arbitrary URIs without a try/except block. Malformed URIs raise `ValueError`. Importantly, catching this and returning the raw string opens the door to CRLF injection, as `ValueError` is raised specifically to block URIs with control characters.
**Learning:** `ValueError` from `urlparse` isn't just a parse failure; it's a security mechanism preventing HTTP Response Splitting. It must be explicitly caught and treated as an invalid/malicious request rather than safely suppressed.
**Prevention:** Wrap `urlparse` calls dealing with potentially untrusted URI generation in a `try...except ValueError` block. Raise or handle the error securely (e.g., returning 400 Bad Request) instead of ignoring it or returning the unparsed, potentially dangerous string.
## 2025-02-21 - Fix SSRF via IPv4-mapped and Non-Global IPv6/IPv4 in _is_public_host
**Vulnerability:** The `_is_public_host` function in `origo/endpoints.py` aims to prevent Server-Side Request Forgery (SSRF) when fetching Client ID Metadata Documents by blocking resolutions to private, loopback, or link-local IPs. However, it used manual checks (`ip.is_private`, `ip.is_loopback`) that fail to block Carrier-Grade NAT (CGNAT, e.g., `100.64.0.0/10`) and other non-global IP spaces in Python 3. Furthermore, IPv4-mapped IPv6 addresses (e.g., `::ffff:192.168.1.1`) might bypass simplistic checks on some network configurations. This allowed attackers to perform SSRF against internal infrastructure residing on non-RFC1918 but still internal/private subnets.
**Learning:** `ipaddress.is_private` is not synonymous with "internal" or "non-routable" on the public internet, particularly for ranges like CGNAT or IETF protocol assignments. Reimplementing public routing logic manually using multiple boolean checks is prone to bypasses.
**Prevention:** Unpack IPv4-mapped IPv6 addresses manually if required, and leverage `not ip.is_global` (alongside existing checks for maximum defense-in-depth) as the definitive indicator of whether an IP is truly meant for the public internet.
